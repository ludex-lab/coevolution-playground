# mb-intervention-voucher

A simulator that reproduces recorded history can still answer a what-if question wrongly: it can apply the change to
a different record than the one asked about, or apply the wrong operator. A replay-only check (arm A) passes such a
simulator. A per-question voucher (arm B) checks each answer against the change that was asked for.

Synthetic named records, scripted simulators, planted faults. This shows the mechanism only. It is not evidence of
any rate and reproduces no paper number.

## Declared rules

- Records are named integer counts. History is a list of events `{record, op, amount}`, where op is add, sub or set.
- A what-if question `{id, record, op, amount}` changes the starting value of the named record and asks for that
  record's final value after the same history. The reference counterfactual is computed by the module itself.
- A simulator reports a replayed final state and, per question, `{applied_to, op, answer}`. Planted faults:
  `wrong_record` (the change goes to another record), `wrong_operator` (for example add instead of set) and
  `drop_last_event` (replay skips the last event).
- Arm A (replay only): PASS iff the replayed final state equals `recorded_final`.
- Arm B (voucher), per question, checked in this order:
  - `applied_to` is not the named record: FAIL.
  - `op` is not the asked operator: FAIL.
  - `answer` is not the reference counterfactual: FAIL.
  - The asked change leaves the start value unchanged (add 0, sub 0, set to the same value): NO_INTERVENTION. This
    is not a FAIL and not a trusted answer.
  - Otherwise: VOUCHED.
- Arm B closes (PASS) iff no question is FAIL and at least one question is VOUCHED.
- Pass rule for the run: the fixture declares the expected table for every simulator before the run. The gate is
  PASS (exit 0) iff the observed arm A, arm B and per-question statuses equal it exactly. Otherwise the run fails
  (exit 1).
- Expected table for `fixtures/main.json`:

| simulator | arm A | arm B | FAIL questions |
|---|---|---|---|
| sim_correct | PASS | PASS | none |
| sim_wrong_record (q_rice applied to barley) | PASS | FAIL | q_rice |
| sim_wrong_operator (q_oil set done as add) | PASS | FAIL | q_oil |
| sim_drop_last_event | FAIL | FAIL | q_barley |

- `q_null` (salt add 0) is the null control. It is NO_INTERVENTION for every simulator, so arm B does not fail on
  it, and it never counts as a trusted answer.
- In both planted what-if faults the reported number equals the reference (17 and 9). Only the target and operator
  checks catch them.
- Bad input is DENY: exit 2, empty stdout, one stderr line `DENY <code>: <detail>`. Ids are type-checked before any
  dict or set lookup, so a list or object id is `bad_type`. Codes: not_json, duplicate_key, unknown_field,
  missing_field, bad_type, bad_version, bad_on_expiry, unknown_record, unknown_question, duplicate_id, bad_op,
  out_of_range, bad_history, bad_fault, bad_expected, too_large (fixture over 32768 bytes), unreadable, usage.
- `on_expiry` must be the literal `DENY`. The mutant runner's timeout is `{"seconds": 300, "on_expiry": "DENY"}`.
  A timeout is not a kill, and crashes are counted separately.

## Files and how to run

- `voucher.py`: module and CLI (`python3 -B voucher.py [--json] fixtures/main.json`).
- `test_voucher.py`: unit tests (`python3 -B -m unittest test_voucher`). No test reads a source file.
- `demo.py`: prints the report for the fixture (`python3 -B demo.py`).
- `mutants.py`: five in-memory mutants, each run in a child `python3 -B` (`python3 -B mutants.py`).
- `evidence.json`: the declared table, measured results and `on_unmeasured`.
- `fixtures/main.json` and `fixtures/bad/*.json` (17 bad fixtures; unreadable and usage are covered by tests).
- `SHA256SUMS`: sha256 of every other file here; run `sha256sum -c SHA256SUMS` inside this folder.
- Stdlib only, no network, no randomness, no model calls.

## Limits

- The simulators are scripted with planted faults; nothing is generated by a model.
- What-if questions only change a starting value. Interventions on events or policies are not modelled.
- The voucher needs a reference counterfactual. Here the module computes it from the declared history; a real
  system would need its own trusted reference.
- One fixture, chosen so the faulty answers match the reference numerically. It shows that the mechanism exists,
  not how often it happens.
- Arm B reads `applied_to` and `op` from the simulator's own report and does not inspect the program. A simulator
  that applies the change to barley but reports rice, with the matching number 17, is VOUCHED (pinned by a test).
  Both planted what-if faults are caught only because the scripted simulators report their real target and
  operator; a real system would need that provenance from instrumentation, not from the simulator's word.
- NO_INTERVENTION is decided on the start value only. A change that a later `set` event overwrites leaves the
  answer equal to the factual value and is still VOUCHED, so such a question cannot tell a simulator that ignores
  the change from one that applies it.

## on_unmeasured (UNVERIFIED)

- On programs written by Haiku and Sonnet in one platform, the paper reports removing 97.6% of wrong answers while
